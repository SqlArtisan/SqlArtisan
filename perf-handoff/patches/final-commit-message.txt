perf: Read each part once in the duplicate-clause walk and index large parameter lists

The duplicate-clause walk still cost the benchmark query about a seventh of its
build: two FrozenDictionary probes and some thirty type tests per part. One
table keyed by exact type now gives a part's role and both its kinds in one
probe, and the exclusive pairs are read through a per-kind mask. The tables the
walk is built from are unchanged, so are its decisions and every message;
RequirementOnlyOnClause, which the type tests matched through its base, is
listed beside it, and DuplicateClauseWalkTests fails for a derived clause or an
ISelectItemsClause / IJoinedRelation implementer the table lacks.

AddParameter scanned every earlier parameter for the instance it was given, so
a statement's build grew with the square of its binds. From 128 parameters the
list is a subclass that finds an instance through a rented open-addressing
index; below that the scan stays, since it is the faster of the two there. The
buffer gains no field. The switch happens where the list was about to grow, so
the array it allocates is the one growth would have; the list object is 48
bytes more, once, for a statement that reaches 129 parameters, and a thread's
first large build allocates the index it later rents back.

Hashing an instance for the first time is what the index costs, and a
statement ending just past the switch would never earn back the cost of
hashing all 128 at once. The entries from before the switch therefore take their
slots two per append and are found by the scan until then, so the cost is
spread over the next 64 parameters. An output parameter is never looked up
again, so it takes no slot and no turn, and the table is sized for every entry
whenever it grows, so a held stage that appends binds after hundreds of output
parameters still finds an empty slot.

A value passed where an expression goes now binds as ImplicitBindValue, an
internal subclass of BindValue made without the public constructor's
reflection check, which a directly bindable value always passes. One exists per
occurrence, so an IN / NOT IN list and a VALUES clause reserve the parameter
list for the ones they hold, unless their first is already bound (the list was
formatted before), at a capacity the list's own doubling would reach. The
smaller arrays are skipped, and the list a statement keeps is the size it was
before. A BindValue the caller holds can repeat one already bound, so it is not
reserved for and grows the list as before. The one repeat the count cannot
tell is an implicit bind read back through SqlParameters.ForEach and passed
again several times in one list: each occurrence is reserved for, so that
statement keeps a larger array than it fills.

The emitted SQL, the parameter names, order and values are unchanged for every
statement.
