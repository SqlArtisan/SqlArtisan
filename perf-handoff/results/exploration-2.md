# 模索 2 回目: 検討済みの案とは別の改善候補

`patches/01`〜`09` と採用・不採用の決定(README の冒頭)を前提に、それ以外の改善余地を
試作と実測で調べた記録。`src/` と `tests/` は変更していない。試作は `patches/explore-*.diff` に
ある(採用版 `patches/adopted-walk-table.diff` を当てた `f428588` に対する差分)。

計測に使った「採用版」は、コミット `859e458` で採用パッチが更新される前の版(SELECT の型一覧を
役割の表に書き写していた版)。更新は静的初期化で一覧を共有するだけで、チェックのループは同じ。
更新後の採用パッチの上でも、試作は 1 本ずつ当たり、`explore-all` を当てたツリーで単体テスト
2,267 / 2,267、`probe` / `stress` / `bindguard` のダイジェスト一致、確保バイト数も同じ値になることを
確かめた。時間は測り直していない。

計測値はすべてクラウドコンテナ(Linux、4 コア、.NET SDK 10.0.115 / ランタイム 10.0.15)上の
相対値。確保バイト数は毎回同じ値になる。

## 1. 結論

- **有望な案が 1 つ見つかった(A1)。** `BindValue` の公開コンストラクタは、値 1 個ごとに
  リフレクションと失敗する型判定で 15〜40 ns を使っている。直接バインドできる型(数値、文字列、
  日時など)を先に通すだけで、検査そのものは残したまま、バインドを含む文が 4〜25% 速くなる。
  変更は 1 ファイル(+5 / −2 行)、確保は不変、測った形で遅くなったものはない。受理・拒否・メッセージは
  値 59 種 × 経路 9 通りで現行と一致した。**採用を勧める。**
- **小粒な案が 5 つある(B、C1、C2、D、E)。** 1 つずつは −1〜6% と −24〜−32 B で、単独では
  計測のばらつきに近い。5 つ合わせるとベンチマークのクエリで −7%、単純な SELECT で −15%、
  確保は文 1 つにつき −80 B になる。採否は複雑さとの兼ね合いで、下の表に 1 つずつ書いた。
- **A1 と小粒 5 つを全部入れた場合**、公式ベンチマーク(BenchmarkDotNet、2 回)は
  採用版 1.413 / 1.518 µs → 1.218 / 1.266 µs、2.27 → 2.19 KB。同じ回の Sqlify は
  1.57〜1.65 µs / 3.13 KB。
- **絶対値では、どれも 1 文あたり 0.05〜0.6 µs の短縮で、DB の往復時間に対しては見えない。**
  意味があるのは README の比較表(時間の列で Sqlify の前に出るかどうか)と、確保量の首位の
  余裕(2.27 → 2.19 KB。首位は現状でも変わらない)に対してだけ。順位が実際に入れ替わるかは
  基準機で測らないとわからない(4 節)。
- **遅くなる形・確保が増える形として見つかったもの**(該当する案の節に詳細):
  A2 のスカラーサブクエリのオペランド(+10〜17 ns)、D の初版の `ParameterNames`(+48 B、
  直した版では −32 B)、E の初回 `Build()` 時の 4 KB(一度だけ)、単一行 INSERT の試作 F の
  ゲート違反。A1、B、C1、C2 では見つかっていない。
- 関数単位のプロファイルは今回も取れていない(5 節)。ここに挙げた以外のホットスポットが
  残っている可能性はある。

| 案 | パッチ | 何を変えるか | 時間(採用版比) | 確保 | 勧めるか |
|---|---|---|---|---|---|
| A1 | `explore-01` | `BindValue` の検査で直接バインド型を先に通す | バインド 1 個 −13〜40 ns。10 列 INSERT −18〜23%、20 値の `IN` −9〜25%、単純な SELECT −4〜7% | 不変 | 勧める |
| A2 | `explore-02`(A1 の上) | リゾルバで直接バインド型をサブクエリ判定より先に見る | 10 列 INSERT でさらに −9〜12%。サブクエリのオペランドは +10〜17 ns | 不変 | 勧めない(デグレが 1 形ある) |
| B | `explore-03` | 引用符つき識別子を 1 回の容量確認で書く | ベンチマークのクエリ −3〜5%、列のない文は差なし | 不変 | 小さいが安全。任意 |
| C1 | `explore-04` | ビルダーのルート句を `params` 配列で渡さない | 単純な SELECT −7%、ほかは −1〜3% | 文 1 つ(とサブクエリ 1 つ)ごとに −32 B | 勧める(単純で確保が減る) |

| E | `explore-07` | 重複句チェックの表引きを型ハンドルの専用表にする | ベンチマークのクエリ −4〜6% | 不変(初回に 4 KB) | 任意(仕掛けが増える) |
| F | なし | 単一行 INSERT の行リストを省く | 測っていない | −56 B | 不採用(ゲートに反する) |

## 2. 案ごとの詳細

時間の表記は「最小値(3〜4 プロセスの最小)」で、単位は ns。変種は 1 プロセスずつ交互に走らせた。
同じ表の中だけで比べること(プロセス内でシナリオを並べる順によって絶対値が変わる)。

### A1: `BindValue` の検査で直接バインド型を先に通す(`explore-01`)

**何を変えるか。** `BindValue` の公開コンストラクタは、値が SqlArtisan のオブジェクトでないことを
`value is SqlPart or ISqlBuilder or ISubquery` と `IsSqlArtisanObject(value.GetType())` で確かめる。
`int` や `string` は多数のインターフェースを実装しているので、失敗するインターフェース判定 2 回が
重く、続く `GetElementType()` / `IsEnum` / `Assembly`(`typeof(BindValue).Assembly` も毎回)が
さらにかかる。試作は、この検査の前に `ExpressionResolver.IsDirectlyBindable(value)` を置き、
真なら検査を飛ばす。アセンブリは静的フィールドに 1 度だけ取る。

**なぜ同じ結果になるか。** `IsDirectlyBindable` が真になるのは `bool`、文字、日時、数値、
`Complex`、列挙、`Guid` だけ。どれも `SqlPart` / `ISqlBuilder` / `ISubquery` ではありえず、
`IsSqlArtisanObject` も偽になる(BCL の型は別アセンブリ、列挙は元の検査でも通す)。検査は
省いておらず、通ることが決まっている値を先に通すだけ。

**パッチ 04(不採用)との違い。** 04 と `ImplicitBindValue` は「暗黙バインドの経路だけ検査を
通らない別のコンストラクタ / 派生クラス」を足す案だった。A1 は公開コンストラクタそのものを
軽くするので、経路も型も増えず、`Sql.Bind`、`Limit` / `Offset` / `Fetch` / `Top`、利用者が直接
書く `new BindValue(x)` にも同じように効く。README の「調べていないこと」にあった
「04 の別案(公開コンストラクタの検査そのものを軽くする)」にあたる。

**実測(採用版 → A1)。**

**遅くなる形・増える確保。** 見つかっていない。直接バインド型でない値は `IsDirectlyBindable` の
判定ぶんだけ余計に通るが、差は測れなかった: `BindArray(int[])` 26 → 27、`new BindValue(byte[])`
26 → 27、`BindNull()` 26 → 26、スカラーサブクエリのオペランド 145 → 145、コンバーター経由の値は
123 → 82(変換後の値が直接バインド型なので速くなる)。バインドのない文(列 20 個の `IN`、NULL 10 個の
INSERT)は ±15 ns の範囲で向きが揃わない。確保は全シナリオで不変。増えるのは静的フィールド 1 つ。

**リスクと複雑さ。** 1 ファイル、+5 / −2 行。公開 API、SQL、パラメータ、例外は変わらない。
単体テスト 2,267 / 2,267、アナライザ 2,166 / 2,166、TableClassGen 336 / 336、DB 不要スライス 69 / 69、
SQLite 501 / 501、`dotnet format --verify-no-changes` 通過。`H.dll bindguard`(値 59 種を
`new BindValue`、`==`、`In`、`+`、`Values`、`Set`、`Select`、`Coalesce`、`Bind` の 9 経路に通した
531 行)が現行と一致。`probe`、`stress`、`mergemsg`、`outloop`、`fuzz` も一致。

**本実装で要ること。** 試作は静的フィールドを既存のコメントと定数の間に置いてしまっている
(位置を直す)。`IsDirectlyBindable` に型を足すとこの検査も緩むので、その依存をコメントで
書く(いまの一覧は 1.0 で固定、と既にコメントがある)。検査が全種別で現行と同じ判定になることを
確かめるテスト(`bindguard` 相当)を単体テストに足す。CHANGELOG は利用者から見える変化が
速度だけなので、書くかはユーザー判断。

**勧めるか。** 勧める。今回の中で、効果に対する変更の小ささと安全性が最もよい。

### A2: リゾルバで直接バインド型を先に見る(`explore-02`、A1 の上に当てる)

**何を変えるか。** `ExpressionResolver.Resolve` と `InsertValueResolver.Resolve` は
`SqlExpression` → `ISubquery` → バインド可能、の順に判定する。`int` などは `ISubquery` の判定
(インターフェース一覧の走査)で 10〜15 ns を使う。試作は直接バインド型の判定を `ISubquery` より
前に移す。型の集合が重ならないので結果は同じ。

**実測(A1 → A2)。** `col == 5` 62 → 45、`col == 5.5m` 55 → 48、10 列 INSERT 1,308 → 1,188 /
1,306 → 1,151、20 値の `IN` 1,702 → 1,546 / 1,427 → 1,432(2 回目は差なし)、単純な SELECT
490 → 452 / 474 → 466。確保は不変。

**遅くなる形。** スカラーサブクエリをオペランドに渡す形(`col == Select(...)...`)が遅くなる。
式の生成だけで 145 → 155〜162(+10〜17 ns)、別の回でも 142 → 149。文全体では 618 → 634、
584 → 620、595 → 611(+2〜6%)。サブクエリは 20 個余りの型判定に全部外れてから判定されるため。
頻出の数種だけを先に見る変種も 2 つ試したが、効果が安定せず(列挙が 47 → 89 になる回があった。
メソッドが大きくなってインライン化が外れたと見ているが、確かめていない)、捨てた。

**勧めるか。** 勧めない。頻用ケースには効くが、現行より遅くなる形が 1 つあり、A1 だけで
効果の大半が出る。入れるなら「サブクエリのオペランドが 1 つにつき約 +10〜17 ns」を承知のうえで。

### B: 引用符つき識別子を 1 回で書く(`explore-03`)

**何を変えるか。** `EncloseInAliasQuotes` は引用符、名前、引用符を 3 回の `Append` で書き、
引用符を方言インターフェースから 2 回読む。試作は引用符を 1 回読み、容量を 1 回確かめて
まとめて書く。`DbColumn.Format` の `"alias".` は続くドットまで 1 回で書く
(`AppendAliasQualifier`)。`EncloseInSpaces` も同じ形にした。README 末尾の未着手点
「引用符を方言インターフェース越しに 2 回読む」にあたる。

**実測(採用版 → B)。** ベンチマークのクエリ 1,372 → 1,310(引用符をフィールドに持つ初版では
1,275 → 1,239)。相関サブクエリ
1,217 → 1,171。列 20 個の `IN` 728 → 687。単純な SELECT 490 → 480。10 列 INSERT は
1,606 → 1,605(列を修飾しないので効かない)。確保は不変。

**遅くなる形・増える確保。** 見つかっていない。引用符をバッファのフィールドに持つ初版は、
D と同時に入れるとバッファが 80 → 88 B になる計算なので、フィールドを足さない形に直した
(パッチはこちら)。

**リスクと複雑さ。** 2 ファイル、+32 / −8 行。内部だけ。出力ダイジェストは一致。

**勧めるか。** 任意。安全だが、識別子の多い文で 3〜5%、ほかでは差が出ない。

### C1: ビルダーのルート句を配列で渡さない(`explore-04`)

**何を変えるか。** すべての文が `new SelectBuilder(params SqlPart[] rootParts)` の形で
1〜2 要素の配列を作り、基底クラスが `List.AddRange` で写している。試作は
`(SqlPart rootPart, SqlPart? secondRootPart = null)` に替える。呼び出し側は全部 1 個か 2 個
(`WITH` つきのときが 2 個)なので、可変長は要らない。

**実測(採用版 → C1)。** 単純な SELECT 490 → 457、ベンチマークのクエリ 1,372 → 1,332、
10 列 INSERT 1,606 → 1,553、サブクエリをオペランドに持つ文 622 → 565。確保は文 1 つにつき
−32 B(サブクエリも 1 つごとに −32 B。`WITH` つきは −40 B の計算だが測っていない)。

**遅くなる形・増える確保。** 見つかっていない。

**リスクと複雑さ。** 6 ファイル、+26 / −12 行。コンストラクタの形が変わるだけで、句の並びは同じ。

**勧めるか。** 勧める。変更が単純で、全文の確保が減る。

### C2: 句の一覧を `List` から配列 + 個数にする(`explore-05`、C1 の上に当てる)

**何を変えるか。** `SqlBuilderBase._parts` を `List<SqlPart>` から `SqlPart[]` と個数に替える。
伸び方は同じ(4 から倍々)。集合演算の継続は、凍結した左側の配列と個数を引き継ぐ。

**実測。** C1 との時間差は測り分けられない(ベンチマークのクエリ 1,332 と 1,348、単純な SELECT
457 と 460)。確保は C1 からさらに −24 B(`List` 32 B が消え、ビルダー本体が 8 B 増える)。

**遅くなる形・増える確保。** 見つかっていない。

**リスクと複雑さ。** `SqlBuilderBase.cs` だけ(+29 / −12 行)だが、`_parts` が `readonly` で
なくなる。集合演算の継続は左側とリストを共有していたのが、配列と個数の写しになる。左側は
凍結済みで以後の描画は必ず例外になるので、単体テスト(`BuilderReuseTests` を含む 2,267 件)と
出力ダイジェストは一致したが、「凍結した左側を読む経路が増えたら古い個数を見る」という前提が
1 つ増える。

**勧めるか。** 任意。−24 B のためにこの前提を増やすかどうか。

### D: パラメータを `List` から配列 + 個数にする(`explore-06`)

**何を変えるか。** `SqlBuildingBuffer` と `SqlParameters` が
`List<KeyValuePair<string, BindValue>>` を持つのをやめ、配列と個数を直接持つ。伸び方は同じ。
パラメータのない文は、共有の空 `SqlParameters` を 1 つ使い回す。README 末尾の未着手点
「`SqlParameters` が配列と個数を直接持てば 24〜32 B 減る見込み」にあたる。

**実測(採用版 → D)。** ベンチマークのクエリ 1,372 → 1,321、10 列 INSERT 1,606 → 1,547、
20 値の `IN` 1,913 → 1,866、単純な SELECT 490 → 485(差なし)。重複検出の走査がスパンの
ループになるので、個数が多いほど効く: 100 値の `IN` 11.5 → 9.7 µs、200 値 34.3 → 26.1 µs、
保持バインド 129 個 20.2 → 15.4 µs。確保は文 1 つにつき −24 B(パラメータの有無によらず)。

`SqlParameters` の読み出し側: `ParameterNames` の列挙は 104 → 72 B で時間も短くなり、`Get<T>` は
14 → 15 ns で差なし。`ForEach` にクロージャを渡す形は 112 → 48 B になった。.NET 10 の JIT が
`ForEach` をインライン化してデリゲート(64 B)をスタックに置けるようになったためと見ている
(公式ベンチマークの Dapper 版も、全部入りで 2.88 → 2.74 KB と、ビルド側の −80 B より 64 B 多く
減った)。この 64 B は .NET 10 の挙動に乗っていて、.NET 8 ランタイムでは確かめていない。

**遅くなる形・増える確保。** 初版は `ParameterNames` を `ArraySegment` 越しに `Select` していて、
列挙 1 回あたり 104 → 152 B に**増えていた**。イテレーターメソッドに直した版(パッチはこちら)で
72 B。`SqlParameters` 本体は 24 → 32 B に増えるが、`List`(32 B)が消えるので差し引き −24 B。
直した版で増える形は見つかっていない。

**リスクと複雑さ。** 3 ファイル、+52 / −28 行。`SqlParameters` と `SqlStatement` の内部
コンストラクタが変わる(公開 API は同じ)。パラメータのない文が同じ `SqlParameters` インスタンスを
共有するようになる(不変なので観測できる違いは参照の同一性だけ)。

**勧めるか。** 任意。頻用ケースでは −24 B と数十 ns。パラメータ 100 個以上の文への効果は
ついでであって、それを理由に入れるものではない(その領域は稀、という前の決定のとおり)。

### E: 重複句チェックの表引きを専用表にする(`explore-07`)

**何を測ったか。** 採用版でも、重複句チェックはベンチマークのクエリで 60〜95 ns、単純な SELECT で
約 40 ns を使っている(チェックの呼び出しを消した切り分け: 1,279 → 1,183、519 → 479)。
大半は `FrozenDictionary<Type, PartTraits>` の検索(句 1 つあたり約 10 ns)。`Validate` は
同じ切り分けで 9〜20 ns(INSERT で 44 ns)しかない。

**何を変えるか。** 表(`TraitsByType`)はそのまま唯一の定義として残し、検索だけを
「型ハンドルの値をキーにした 256 スロットのオープンアドレス表」に替える。表は静的初期化で
`TraitsByType` から組み立てる。

**パッチ 01 と代案(検討済み)との違い。** 01 は句クラスごとの仮想プロパティで種別を持つ案で、
表とクラスがずれる懸念があった。E はクラスに何も足さず、種別の出どころは採用版の表のまま。
替わるのは検索の入れ物だけなので、`DuplicateClauseWalkTests` の網羅ゲートはそのまま効く。

**実測(採用版 → E)。** ベンチマークのクエリ 1,372 → 1,284、1,275 → 1,227。相関サブクエリ
1,217 → 1,145。`LIMIT` + `OFFSET` 619 → 570。単純な SELECT 490 → 471。10 列 INSERT は
1,606 → 1,615(差なし)。確保は不変。

**遅くなる形・増える確保。** 文ごとの確保は増えない。プロセスで 1 度だけ、表の 4 KB と
その組み立て(最初の `Build()` の静的初期化)が増える。初回 `Build()` の時間への影響は測っていない。

**リスクと複雑さ。** `SqlBuilderBase.cs` に +41 行。`Type.TypeHandle.Value` と乗算ハッシュという
仕掛けが増える。型ハンドルは型が生きている間は変わらないが、NativeAOT とトリミング下での
動作は確かめていない(`Directory.Build.props` は AOT 互換を掲げている)。

**勧めるか。** 任意。ベンチマークのクエリで 4〜6% は小粒の中では大きいが、読み手が理解すべき
仕掛けが増える。README の時間の列を詰めたいなら候補、そうでなければ見送りでよい。

### F: 単一行 INSERT の行リストを省く(不採用)

`InsertValuesClause` は 1 行でも `List<SqlExpression[]>` と 1 要素の配列(計 64 B)を作る。
最初の行をフィールドに持ち、2 行目からリストを作る形にすると単一行で −56 B(2,064 → 2,008 B)。
ただし遅延生成のフィールドが `readonly` にできず、`SqlPartImmutabilityTests`(`SqlPart` の
インスタンスフィールドはすべて `readonly`)に落ちる。リポジトリの不変条件に反するので不採用。
時間は測っていない。

## 5. 試作も計測もしていない、または途中でやめたもの

- **関数単位のプロファイル。** EventPipe のサンプルプロファイラ(環境変数で有効化、
  `Microsoft.Diagnostics.Tracing.TraceEvent` で集計)は動いたが、サンプルが GC のセーフポイントに
  しか落ちず、ほぼ全部が配列コピーのヘルパーに計上されて使えなかった。`perf` の導入は権限で
  拒否された。切り分けは前回と同じく、処理を消すか差し替えた変種で行った。
- **`Validate` の走査削減**(README「03」節の未着手点)。`Validate` を丸ごと消した上限が
  SELECT で 9〜20 ns、10 列 INSERT で 44 ns だったので、試作していない。
- **`ToDynamicParameters` のクロージャ**(`SqlArtisan.Dapper`)。`SqlArtisan` は
  `SqlArtisan.Dapper` に内部を公開していないので、なくすには状態を渡せる列挙の公開 API が要る。
  試作していない。D を入れると .NET 10 ではデリゲートの 64 B が消える(上記)。
- **`BindValue` を 48 → 40 B にする**(`DbType?` / `Direction?` / `Size?` を詰める)。計算上
  バインド 1 個につき −8 B。公開型の内部レイアウトの変更で、試作していない。
- **値のボックス化**(`object` 引数。バインド 1 個につき 24 B)と `params object[]`。
  なくすには型つきオーバーロードが要り、公開 API が増える。README の既知の点と同じ。
- **`ArrayPool<char>` の貸し借りだけをスレッド単位にする**(パッチ 05 のうち、バッファ本体は
  使い回さない形)。`ArrayPool.Shared` 自体がスレッドローカルのキャッシュを持つので効果は
  小さいと見て、測っていない。
- **確かめていないこと。** コンテナを使う結合テスト(MySQL、Oracle、PostgreSQL、SQL Server)、
  基準機での公式ベンチマーク、.NET 8 ランタイムでの時間と確保(このコンテナには .NET 10 しかない)、
  NativeAOT、試作に対する独立したレビューと変異テスト。試作にはテストもコメントも CHANGELOG も
  付けていない。

## 6. 再現手順

```bash
# 採用版を当てたツリーを作り、試作を当てる
git worktree add /tmp/sa-adopted f428588
(cd /tmp/sa-adopted && git apply /path/to/perf-handoff/patches/adopted-walk-table.diff)
git worktree add /tmp/sa-a1 f428588
(cd /tmp/sa-a1 && git apply /path/to/perf-handoff/patches/adopted-walk-table.diff \
    && git apply /path/to/perf-handoff/patches/explore-01-bindvalue-direct-check.diff)

# ハーネスを変種ごとにビルドして、1 プロセスずつ交互に走らせる
cd perf-handoff/harness
dotnet build -c Release -o out/adopted -p:SaPath=/tmp/sa-adopted/src/SqlArtisan/SqlArtisan.csproj
dotnet build -c Release -o out/a1 -p:SaPath=/tmp/sa-a1/src/SqlArtisan/SqlArtisan.csproj
python3 cmp.py 4 5 bindInt,full,simple,insert10,in20,eqInt,eqSubquery adopted a1

# 値の種類ごとの受理・拒否・メッセージ(変種間で diff する)
dotnet out/adopted/H.dll bindguard > /tmp/bg-adopted.txt
dotnet out/a1/H.dll bindguard > /tmp/bg-a1.txt
```

- `cmp.py <プロセス数> <ラウンド数> <シナリオ,…> <変種…>` は `out/<変種>/H.dll` を 1 本ずつ
  交互に走らせ、最小値 / 中央値と確保を並べる。`CMP_RAW=<ファイル>` で生の行を逐次書き出す。
- 先頭のシナリオは起動直後で遅く出るので、捨て石(`bindInt` など)を先頭に置く。
- 今回足したシナリオ: `eqInt` / `eqString` / `eqLong` / `eqDecimal` / `eqDate` / `eqEnum` / `eqGuid` /
  `eqCol` / `eqSubquery`(式の生成だけ)、`eqSubqueryBuild`、`convBind` / `convBuild`(値コンバーター)、
  `bindArr`、`insertSub`、`updateSet3`、`deleteWhere`、`limitOffset`、`paramNames` / `paramForEach` /
  `paramGet`。
- パッチは採用版に 1 本ずつ当たる。`explore-02` は `01` の上、`explore-05` は `04` の上。
  `explore-07` を `05` のあとに当てるときは `git apply --3way`。`explore-all` は
  01 + 03 + 04 + 05 + 06 + 07 をまとめたもの(02 は含まない)。
