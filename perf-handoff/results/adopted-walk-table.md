# 採用版(重複句チェックの表の一本化だけ)の検証

対象は `patches/adopted-walk-table.diff`(`f428588` に当てる 1 コミット分、コミット文は
`patches/adopted-walk-table-commit-message.txt`)。

採否の決定(ユーザー判断):

| 施策 | 決定 | 理由 |
|---|---|---|
| 重複句チェックの表の一本化 | 採用 | 全文に効き、確保は変わらず、レビューでデグレが一度も出ていない |
| 暗黙バインドと容量の事前確保 | 不採用 | デグレが 3 件出た部分で、短縮は 1 文あたり 0.1〜0.5 µs。記録は `results/declined-reservation.md` |
| 128 個以上でのハッシュ索引 | 不採用 | 128 個以上のパラメータを持つ文は稀。記録は `results/panel-audit.md` |

計測値はクラウドコンテナ(.NET 10)上の相対値。確保バイト数は毎回同じ値になる。

## 1. 中身

変更は `SqlBuilderBase.cs`(+165 / −46 行)とテスト 2 ファイル(+105 行)。差分全体は
3 ファイル、+270 / −46 行。`SqlBuildingBuffer`、`BindValue`、`IN` / `VALUES` の各句、CHANGELOG には
触れない。

- 厳密な型をキーにした表 1 つ(`TraitsByType`)から、句の役割と 2 種類の種別を 1 回で引く。
  現行は `FrozenDictionary` を 2 回引き、型判定を 30 回ほど行っていた。
- 排他ペアは種別ごとのビットマスクで判定する。違反を見つけたあとのメッセージ組み立ては
  元の表(`ExclusiveKinds` / `ExclusiveBranchKinds`)を表の順に読むので、文言は現行と同じ。
- SELECT の役割は、種別の表の `"SELECT"` エントリの型一覧をそのまま参照する(同じ 6 型を 2 か所に
  書かない)。これで、種別の表から SELECT 句の型が漏れた場合も `DuplicateClauseWalkTests` が落ちる。
  現行にはこの漏れを検出するものがなかった(下の 6 節)。
- 型判定が基底クラス越しに拾っていた `RequirementOnlyOnClause` は表に並べて載せた。
  表に載っていない派生クラスや、`ISelectItemsClause` / `IJoinedRelation` の実装が増えると
  `DuplicateClauseWalkTests` が落ちる。

## 2. ゲート

- `dotnet build SqlArtisan.sln -c Release`: エラー 0(警告 20 は現行と同じ)。
- 単体テスト 2,267 / 2,267、`SqlArtisan.Analyzers.Tests` 2,166 / 2,166、
  `SqlArtisan.TableClassGen.Tests` 336 / 336、`dotnet format --verify-no-changes` 終了コード 0。
- 結合テストの DB 不要スライス 69 / 69、SQLite 501 / 501。
- 現行との出力一致: `H.dll probe`、`stress`(5 方言 20,000 文 × 並列 3 周、ダイジェスト一致)、
  `mergemsg`、`outloop 130 600`。
- 変異テスト 12 本: ブロックと分岐それぞれの「重複の判定を外す」「排他の判定を外す」「見た種別を
  記録しない」、JOIN 条件の重複と欠落の判定を外す、`InsertIgnoreIntoClause` の役割を落とす、
  MERGE 分岐の排他ペアを逆順に読む、種別の表の SELECT から `SelectClauseWithTop` を落とす、の
  11 本はテストが落ちる。ブロックの排他ペアを逆順に読む 1 本は
  通るが、ブロックの種別は排他の相手が 1 つずつしかないのでメッセージは変わらない(等価な変異)。
- 追加したテスト: `DuplicateClauseWalkTests`(表の網羅)、`BuilderReuseTests` の 2 件
  (保持した INSERT IGNORE ステージ、排他の相手が 2 つある MERGE 分岐で名指しされるペア)。

## 3. 計測(3 プロセスを交互に実行、ns)

「一覧共有前」は SELECT の 6 型を 2 か所に書いていた版で、実行時のコードは採用版と同じ。

| シナリオ | 現行 `f428588` | 一覧共有前 | 採用版 | 確保 |
|---|---|---|---|---|
| ベンチマークのクエリ(PostgreSQL) | 1,004〜1,068 | 947〜977 | 929〜989 | 2,352 B のまま |
| 同(Oracle) | 1,068〜1,103 | 986〜1,012 | 958〜999 | 2,320 B のまま |
| 同(SQL Server) | 1,082〜1,121 | 1,010〜1,034 | 992〜1,028 | 2,320 B のまま |
| 単純な SELECT | 409〜432 | 388〜405 | 382〜449 | 832 B のまま |
| NULL 10 個の INSERT | 585〜593 | 561〜578 | 529〜561 | 1,168 B のまま |
| 列 20 個の `IN` | 600〜622 | 581〜637 | 622〜626 | 1,128 B のまま |
| 10 列 INSERT | 1,298〜1,339 | 1,269〜1,307 | 1,288〜1,306 | 2,064 B のまま |
| 20 値の `IN` | 1,500〜1,580 | 1,372〜1,529 | 1,475〜1,509 | 3,496 B のまま |

- ベンチマークのクエリは最小値どうしの比で 0.90〜0.93。句の少ない文は 0.90〜0.93 か、区別がつかない
  (列 20 個の `IN` は採用版 622 に対し現行 600〜622)。
- 効くのは句の数に比例する部分だけなので、バインドが時間の大半を占める文(値の多い `IN`、
  出力パラメータの多い文)は現行と区別がつかない。一覧共有前の版の計測では、100 値の `IN`、
  保持バインド 129 個の `IN`、出力パラメータ 300 個、1,000 値の `IN` がいずれも現行と同じ水準だった。
- 確保バイト数は、測ったすべての形で現行と同じ。

## 4. 取り込み時に必要なこと

- CHANGELOG の未リリース項目「`Build()` finds each clause's kind with one lookup … about 15% faster」は
  #845 の変更を表しており、文章はこの変更後も正しい。数字だけが #845 時点のもので、この変更で
  さらに速くなる。基準機で公式ベンチマークを測り直して同じ項目の数字を差し替える(測らないなら
  数字を消す)。README のベンチマーク表も同じ。パッチはどちらも変えていない。
- コンテナを使う結合テスト(MySQL、Oracle、PostgreSQL、SQL Server)を CI で通す。

## 5. 確かめていないこと

- 最終状態に対する、レビューだけを目的とした独立した席。テスト 2 ファイルは索引あり版の最終状態と
  バイト単位で同じで、`SqlBuilderBase.cs` はそこから SELECT の一覧の 1 か所(5 行 → 2 行)だけが違う。
  その 1 か所は 6 節の独立エージェントが実装して検証したもの。
- コンテナを使う結合テスト、基準機での公式 BenchmarkDotNet、.NET 8 ランタイムでの時間。

## 6. 別案との比較(独立エージェント)

同じ施策の別の設計書(`results/compared-alternative-plan.md`)と比べた。エージェントには、どちらを
誰が書いたかも既存の評価も伝えず、別案を設計書どおりに実装させて同じ条件で確かめさせた。

- 結論: 単独ならこのパッチ(一覧共有前の版)が別案より優れる。別案の「SELECT の型一覧を 1 か所に
  持つ」を取り込んだ形がいちばん良い。採用版はその形である。
- 正しさ: 句の並び約 698 万通り(違反が重なる列、排他の相手が複数ある MERGE 分岐を含む)で、
  現行・このパッチ・別案の判定と例外メッセージ(63 種)が一致。
- 性能: `Build()` 全体では両案とも現行より 6〜8% 速く、両案の差は MERGE と INSERT … VALUES 以外では
  区別できない。チェック単体ではこのパッチが速い(ベンチマークのクエリ 118 → 51 ns、別案 59 ns。
  MERGE は 128 → 55 ns、別案 99 ns)。差の原因は排他ペアをビットマスクで読むかどうかだけ。
- 一覧共有の根拠: 種別の表の SELECT から `SelectClauseWithTop` を外す変異が、一覧共有前の版では
  全テストを通った(こちらでも再実行して確認)。採用版では 2 件落ちる。
- 取り込まなかったもの: 別案の `[Flags]` の役割と `PartTraits.None`(性能は区別できず、1 型 1 役割が
  構造で保証されるほうを残した)。エージェントは CHANGELOG の「約 15%」を「約 20%」に書き換える案も
  示したが、コンテナでの相対値から置いた仮の数字なので入れていない(4 節のとおり基準機で測る)。
