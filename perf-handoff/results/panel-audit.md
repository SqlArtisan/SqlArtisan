# パネルレビューの記録と最終版の計測

対象は `patches/final-walk-table-and-parameter-index.diff`(`f428588` に当てる 1 コミット分)。
試作(`patches/01`〜`09`)をそのまま積んだものではなく、レビューで見つかった問題を直して
書き直した実装である。

計測値はすべてクラウドコンテナ(Linux、4 コア、.NET 10 ランタイム)上のもので、相対比較としてだけ
読むこと。確保バイト数は `GC.GetAllocatedBytesForCurrentThread` による値で、毎回同じになる。

## 1. 最終版の中身

| 対象 | 変更 |
|---|---|
| 重複句チェック(`SqlBuilderBase`) | 厳密な型をキーにした表 1 つから、句の役割と 2 種類の種別を 1 回で引く。排他ペアは種別ごとのビットマスクで判定。元の表と例外メッセージはそのまま |
| パラメータの重複検出(`SqlBuildingBuffer`) | 128 個までは線形走査のまま。リストが満杯で 129 個目が来たとき、借り物の配列を使うハッシュ索引つきの `List<>` 派生クラスに切り替える。バッファにフィールドは増えない |
| 索引の構築 | 切り替え前の 128 個は、以後の追加 1 回につき 2 個ずつ索引に入れる(それまでは走査で見つける)。一括で入れると 129〜140 個前後の文が現行より遅くなったため |
| 出力パラメータ | 二度と検索されないので索引に入れない。索引は拡張のたびに全エントリ分の大きさで作り直すので、出力パラメータが何百個あっても空きスロットが尽きない |
| 暗黙バインド | 値をそのまま渡したときのバインドを内部クラス `ImplicitBindValue` にする(公開コンストラクタの型検査を省く)。`IN` / `NOT IN` / `VALUES` はこの個数だけ先にリスト容量を確保する。呼び出し側が持つ `BindValue` は数えない |

## 2. 無限ループの件

- 試作 06 の無限ループは実在した。バインド 32 個 → 出力パラメータ 223 個以上 → バインド、の順で
  描画される文(保持した UPDATE のステージに `Returning(...).Into(...)` を足してから `Where` を続ける形)で
  `Build()` が戻らない。`H.dll outloop 32 223` で再現(試作は 60 秒でタイムアウト、現行は即座に戻る)。
- 最終版では起きない。根拠は 3 つ。
  1. 不変条件: スロットに入るのは「追加時点で表の半分以下」のエントリだけで、作り直しは全エントリ数の
     4 倍以上の大きさで行う。したがって探索は必ず空きスロットに当たる。
  2. 単体テスト `Returning_Oracle_HeldStageBindsAfterManyOutputParameters_CorrectSql`(バインド 130 個、
     出力 600 個、そのあとバインド)。出力パラメータを拡張判定なしで索引に入れる変異を入れると
     テストスイートがハングする(= 再発すれば CI が止まる)。
  3. ランダム差分テスト `H.dll fuzz <本数> <最大ステップ>`: 内部バッファを直接操作し、新規バインド、
     既出バインドの再利用、出力パラメータ、数の合わない容量確保を、長い連続を含む乱数列で与える。
     3,000 本(225 万ステップ、最大 77,600 パラメータ)で現行と最終版の出力ダイジェストが一致。
     同じ乱数列で試作 06 はハングする(= このテストは問題の形に届いている)。
     最終版だけで 40,000 本(2,400 万ステップ)も完走。

## 3. パネル(3 モデル)の指摘と判定

第 1 ラウンドは修正版(v2)に対して Sonnet / Opus / Fable の 3 席に同一の指示で依頼した。3 席とも戻り、
3 席とも「`f428588` との挙動差なし」。指摘は以下で、すべて計測で再確認したうえで直した。

| 指摘 | 挙げた席 | 判定 | 対処 |
|---|---|---|---|
| 同じ `BindValue` を繰り返す一覧で、容量確保が実際より多く数える(同一バインド 300 個の `IN`: 5,544 → 13,688 B、時間も増える) | Sonnet, Opus, Fable | CONFIRMED | 数えるのを暗黙バインドだけにし、一覧の先頭が既出なら確保しない |
| 索引つきリストへの切り替えで +48 B。コメント・コミット文・CHANGELOG が「増えない」と読める | Opus, Fable | CONFIRMED | 文言を実態(129 個に達する文で 1 回 +48 B、スレッド最初の大きな文で索引を確保)に直した |
| 古くなったコメント(存在しないテスト名 `PartTraitsTests`、`_parameters` の説明) | Opus, Fable | CONFIRMED | 修正 |
| 索引の拡張後の検索を確かめるテストがない(拡張で既存エントリを落とす変異が全テストを通る) | Fable | CONFIRMED | 257 個・1,025 個をまたぐテストを追加 |
| `InsertIgnoreIntoClause` を役割の表から落としても気づけない | Fable | CONFIRMED | テストを追加 |
| 出力パラメータ 100〜300 個の `RETURNING … INTO` が 4〜13% 遅い(Fable は「稀な形なので変更は求めない」とした) | Fable | CONFIRMED(再計測で 7〜10%) | 出力パラメータを索引に入れない形に変更 |
| `byte[]` / `DBNull` / 配列の `BindValue` 生成が 6〜9 ns 遅い(計測の記載のみ、変更要求なし) | Fable | CONFIRMED | 公開コンストラクタを元の形に戻した |

Sonnet の指摘は 1 件目だけだった。「指摘なし」は他の席の指摘を否定する票としては扱っていない。

直したあとに自分で見つけたもの: 容量確保の呼び出しで引数の評価順を誤り、`IN` の確保が一度も
効いていなかった(変異テストが生き残ったことで発覚)。直したうえで、確保が効いていないと落ちる
テスト(確保バイト数の差を正確に比べる)を追加した。

最終確認(修正後の状態を新規の 1 席に依頼)の指摘:

| 指摘 | 判定 | 対処 |
|---|---|---|
| 索引を外しても、返却をやめても、`VALUES` / `NOT IN` の確保を外してもテストが通る(変異 9 本が生存) | CONFIRMED(同じ変異を再実行して確認) | 保持リストの型、借りた索引の返却、切り替え時の容量を確かめるテストを追加。変異 20 本すべて検出 |
| 「暗黙バインドは必ず新しいパラメータ」は言い過ぎ。`SqlParameters.ForEach` で取り出したインスタンスを同じ一覧で繰り返すと、その回数分が確保される(SQL とパラメータは同じ、保持する配列だけ大きい) | OVERREACH(事実。届くのは取り出したバインドを繰り返し渡す場合だけ) | コメントとコミット文に例外として明記し、その形をテストで固定 |
| 129〜145 個を 1 個ずつ追加する文が現行より 3〜15% 遅い(最大約 1.5 µs)。レビュー担当は「変更を求めない」とした | CONFIRMED(下の 4.2 で再現) | 索引への登録を 1 回の追加につき 2 個ずつに分散。この帯で現行より遅い形はなくなった |
| README のベンチマーク表と CHANGELOG の「約 15%」を測り直すか | ユーザー判断 | 未対応。公式ベンチマークを基準機で回す必要がある |

## 5. 残っているコスト(最終版で意図して受け入れたもの)

- 129 個目のパラメータに達する文で、1 回だけ +48 B(索引つきリストのオブジェクト)。
  1 個ずつ追加する場合も、容量確保で最初から索引つきになる場合も同じ。
- スレッドごとに、最初の大きな文で索引の配列(512 要素〜)を 1 回確保する。以後は借りて返す。
- `SqlParameters.ForEach` で取り出した暗黙バインドを同じ一覧で繰り返すと、繰り返した回数分の
  容量が確保される(SQL とパラメータは変わらない)。
- AND 条件 150 個や出力パラメータ 300 個の文は、現行と区別がつかない(速くも遅くもない)。

## 6. ゲートと変異テスト(最終版)

- `dotnet build SqlArtisan.sln -c Release`: エラー 0。
- 単体テスト 2,307 / 2,307、`SqlArtisan.Analyzers.Tests` 2,166 / 2,166、
  `SqlArtisan.TableClassGen.Tests` 336 / 336、`dotnet format --verify-no-changes` 終了コード 0。
- 結合テストの DB 不要スライス 69 / 69、SQLite(`Engine=Sqlite`)501 / 501。
- `H.dll stress`(5 方言 20,000 文 × 並列 3 周)の出力ダイジェストが現行と一致。
- 変異テスト 20 本(索引に切り替えない、確保で索引を作らない、しきい値を 4,096 にする、索引を返さない
  2 通り、`VALUES` / `NOT IN` / `IN` の確保を外す、切り替え時の容量を 4 倍にする、待機中エントリの走査を
  外す、登録順を誤る、1 回あたりの登録数を 0 / 1 にする、すべての `BindValue` を数える、作り直しで
  256 個目以降を落とす、作り直し後も待機数を残す、コンストラクタで待機数を 0 にする、先頭既出の判定を
  外す、`InsertIgnoreIntoClause` の役割を落とす、出力パラメータを索引に入れる)はすべてテストが落ちる。

## 7. 確かめていないこと

- コンテナを使う結合テスト(MySQL、Oracle、PostgreSQL、SQL Server)。Docker がない。
- 公式の BenchmarkDotNet(基準機での README の表)。
- .NET 8 ランタイムでの時間(入っているのは .NET 10 だけ。ライブラリのターゲットは `net8.0`)。
- アナライザーの性能と `SqlArtisan.ArrayBind` の経路。
