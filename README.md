A type-safe SQL query builder for MySQL, Oracle, PostgreSQL, SQLite and SQL Server, with an opt-in Roslyn analyzer that flags dialect and schema mistakes at build time — the SQL you write is the SQL that runs, allocation-light, fast, and automatically parameterized.

---

## Why SqlArtisan?

Does this sound familiar?

> - Your ORM can't express the query, so you fall back to raw SQL strings.
> - Building a query dynamically means concatenating strings through your logic.
> - Every value needs a hand-written `DbParameter` — tedious and easy to get wrong.

SqlArtisan lets you write that SQL in C# instead: the query reads as the SQL it emits, conditions join with plain C# instead of string concatenation, and literals become bind parameters automatically.

When an AI coding assistant writes your SQL, a new failure mode appears: plausible queries that look right but mix dialects, misname columns, or silently change semantics. SqlArtisan is a deterministic guard rail — four verification layers catch these mistakes before the query reaches a database:

1. **Types** — column names and statement structure are compile-checked; a wrong name fails the build.
2. **Analyzer** — the opt-in Roslyn analyzer, shipped inside the `SqlArtisan` package, flags constructs your target dialect does not support. With generated table classes it also flags schema hazards, such as `IS NULL` on a `NOT NULL` column or a text column compared to a number.
3. **Exact-SQL tests** — `Build()` is deterministic, so a unit test pins the reviewed SQL as a regression contract.
4. **Integration matrix** — analyzer entries are run against live engines, apart from a few named exceptions ([CI gates](https://github.com/SqlArtisan/SqlArtisan/blob/main/docs/analyzer.md#ci-gates-and-stricter-enforcement)).

```csharp
bool filterByDate = true; // e.g. a search-form checkbox
UsersTable u = new();

SqlStatement sql =
    Select(u.Id, u.Name, u.CreatedAt)
    .From(u)
    .Where(
        u.Name.Like("A%")
        & ConditionIf(filterByDate, u.CreatedAt >= new DateTime(2026, 1, 1)))
    .Build();

// SELECT id, name, created_at FROM users WHERE (name LIKE :0) AND (created_at >= :1)
```

Building a statement costs little — see [Performance](#performance).

### Installation

Packages are pre-release, so pass `--prerelease`:

```bash
dotnet add package SqlArtisan --prerelease           # core query builder
dotnet add package SqlArtisan.Dapper --prerelease    # optional: Dapper execution
dotnet add package SqlArtisan.ArrayBind --prerelease # optional: Oracle array-bind execution
```

To generate table classes from an existing database, install `SqlArtisan.TableClassGen` as a local tool, pinned in the repository that holds the generated classes. Its [README](https://github.com/SqlArtisan/SqlArtisan/blob/main/src/SqlArtisan.TableClassGen/README.md) covers its options and `--check`, which reports where the classes have drifted from the live schema.

```bash
dotnet new tool-manifest                                  # once per repository
dotnet tool install SqlArtisan.TableClassGen --prerelease
```

### Quick Start

1. Define your Table Class

    Create a C# table class for each database table to enable IntelliSense and prevent typos in names. Write it manually (see below) or generate it from an existing database with the `SqlArtisan.TableClassGen` tool. (For a one-off query you can skip the class and name a table inline with `DbTable`.)

    ```csharp
    using SqlArtisan;
    // ...

    internal sealed class UsersTable : DbTableBase
    {
        public UsersTable(string tableAlias = "") : base("users", tableAlias)
        {
            Id = new DbColumn(this, "id");
            Name = new DbColumn(this, "name");
            CreatedAt = new DbColumn(this, "created_at");
        }

        public DbColumn Id { get; }
        public DbColumn Name { get; }
        public DbColumn CreatedAt { get; }
    }
    ```

2. Define your DTO Class

    A plain class with settable properties, which Dapper fills by column name:

    ```csharp
    internal sealed class UserDto
    {
        public int Id { get; set; }
        public string Name { get; set; } = "";
        public DateTime CreatedAt { get; set; }
    }
    ```

3. Build and Execute your Query

    Add `using static SqlArtisan.Sql;` for the entry-point methods (`Select`, `InsertInto`, …), build the query — the one at the top of this page, without `Build()`: the Dapper extension builds it for the connection's dialect — and execute it, here with Dapper:

    ```csharp
    using SqlArtisan;
    using SqlArtisan.Dapper;
    using static SqlArtisan.Sql;
    // ...

    bool filterByDate = true; // e.g. a search-form checkbox
    UsersTable u = new();

    ISqlBuilder sql =
        Select(u.Id, u.Name, u.CreatedAt)
        .From(u)
        .Where(
            u.Name.Like("A%")
            & ConditionIf(filterByDate, u.CreatedAt >= new DateTime(2026, 1, 1)));

    // Dapper: Set true to map snake_case columns to PascalCase/camelCase C# members.
    Dapper.DefaultTypeMap.MatchNamesWithUnderscores = true;

    // 'connection' is your IDbConnection. SqlArtisan detects the DBMS from it
    // and applies its bind-parameter prefix (e.g., ':' or '@').
    IEnumerable<UserDto> users = await connection.QueryAsync<UserDto>(sql);
    ```

    **Note:** `sql` above is single-use — `Build()` runs inside `QueryAsync` (and every other Dapper call) the moment you call it, so passing the same `sql` to a second call, e.g. to fetch another page, throws. Build a fresh query per call instead. See [Reusing a builder chain](https://github.com/SqlArtisan/SqlArtisan/blob/main/docs/query-statements.md#reusing-a-builder-chain).

    **Alternative: Manual Execution**

    Not using Dapper? Call `Build()` to get the SQL string and its parameters for raw ADO.NET, another micro-ORM, or debugging. `Build()` takes an optional `Dbms` (default `PostgreSql`) that sets dialect details like the parameter prefix.

    ```csharp
    SqlStatement sql = Select(u.Id, u.Name).From(u).Where(u.Id == 10).Build();
    // sql.Text       => "SELECT id, name FROM users WHERE id = :0"
    // sql.Parameters => ":0" is 10
    ```

    **Note:** the single-use rule above applies here too — calling `Build()` twice on the same instance throws.

    On Oracle, set `OracleCommand.BindByName = true` when you bind `sql.Parameters` yourself: ODP.NET binds by position by default, so a statement that repeats a marker ahead of another (one `Bind(...)` value used twice) does not run (observed with ODP.NET 23.8 on Oracle XE 21.3.0).

## Configuration

### Setting the Default DBMS

`Build()`'s `Dbms` argument defaults to PostgreSQL. Set a global default once at startup instead of passing it in every call.

```csharp
// At application startup
SqlArtisanConfig.SetDefaultDbms(Dbms.SqlServer);

// Now, Build() without arguments will generate SQL Server-compatible SQL
SqlStatement sql = Select(u.Name).From(u).Build();
```

**Note:** `SqlArtisanConfig` is not thread-safe and should be configured only once at application startup.

### Enabling the Analyzer

The analyzer bundled in `SqlArtisan` reports nothing on your code until you name a target dialect. Add one line to `.editorconfig`:

```ini
[*.cs]
sqlartisan_syntax_postgresql = 16   # engine version, or `any` for no version bound
```

This is separate from `SetDefaultDbms`: that call sets the dialect `Build()` emits at run time, while the analyzer reads only `.editorconfig` or an MSBuild property at compile time. See [Enabling it](https://github.com/SqlArtisan/SqlArtisan/blob/main/docs/analyzer.md#enabling-it) for the other dialects' keys, the MSBuild form, and checking several dialects at once.

## Design Philosophy

SqlArtisan's principle is simple: **the SQL you write is the SQL that runs.** Full ORMs hide SQL behind object graphs, and portability-focused builders rewrite your query per database; SqlArtisan maps your C# straight to SQL, with no translation layer second-guessing your intent.

It normalizes only mechanical dialect details — bind-parameter markers (`:0` vs `@0`), alias quoting (`"` vs MySQL's backtick), and same-meaning token spellings such as the UPSERT excluded-row name — and never rewrites SQL grammar. Where dialects diverge, it exposes distinct, dialect-faithful APIs:

```csharp
Sequence("users_id_seq").Nextval   // Oracle:      users_id_seq.NEXTVAL
Nextval("users_id_seq")            // PostgreSQL:  NEXTVAL('users_id_seq')
NextValueFor("users_id_seq")       // SQL Server:  NEXT VALUE FOR users_id_seq
```

So **cross-database portability is a deliberate non-goal**: target Oracle and you write Oracle SQL; target PostgreSQL and you write PostgreSQL SQL. You trade portability for fidelity — the full power of your database's SQL, never flattened to a lowest common denominator.

## Performance

Every entrant builds the same query's SQL string **and** its bind parameters, measured with [BenchmarkDotNet](https://benchmarkdotnet.org/). SqlArtisan is the **lowest-allocation** builder — it recycles string buffers from `ArrayPool<T>` — and only a hand-written `StringBuilder`, with no type safety, allocates less. Its build time sits among the lightweight builders and an order of magnitude ahead of linq2db and SqlKata.

| Builder | Parameters | Mean | Allocated |
| :--- | :--- | ---: | ---: |
| `StringBuilder` (baseline¹) | Dapper `DynamicParameters` | 305.2 ns | 1.87 KB |
| **SqlArtisan** | its own (`SqlParameters`) | 1,227.1 ns | **2.23 KB** |
| **SqlArtisan** | Dapper `DynamicParameters` | 1,100.4 ns | 2.85 KB |
| Sqlify | its own | 975.4 ns | 3.13 KB |
| Dapper.SqlBuilder | Dapper `DynamicParameters` | 1,261.6 ns | 4.80 KB |
| InterpolatedSql | its own | 1,386.7 ns | 4.95 KB |
| linq2db | its own | 21,070.9 ns | 14.92 KB |
| SqlKata | its own | 38,031.3 ns | 54.01 KB |
| EF Core (ORM reference²) | the `DbCommand`'s | 25,648.2 ns | 15.71 KB |

The lightweight builders allocate the same bytes every run; times do not repeat. Across three runs an entrant's time varied by up to about 40%: Sqlify beat both SqlArtisan entrants in two, Dapper.SqlBuilder in one, and no builder in the third. The table shows one run, builders sorted by allocation. *Parameters* is the collection an entrant's bind values end up in: SqlArtisan appears twice, once with its own and once converted to Dapper's, the form `SqlArtisan.Dapper` passes on.

¹ Raw `StringBuilder` + Dapper `DynamicParameters` — the floor, with no type safety or dialect handling. ² EF Core is a full-ORM **reference** (different work, caches compiled queries), shown only for scale.

*Measured 2026-11-20 on .NET 10.0.15 (SDK 10.0.109) with BenchmarkDotNet 0.15.8, i5-1135G7 / 16 GB / Windows 11 25H2, PostgreSQL dialect. Query shape, library versions, each row's benchmark method, and re-run instructions are in the [benchmark project's README](https://github.com/SqlArtisan/SqlArtisan/blob/main/tests/SqlArtisan.Benchmark/README.md).*
